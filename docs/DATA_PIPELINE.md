# Data pipeline

The corpus is generated from fixed C++ rules only. No real-world files, host
randomness, locale-sensitive text conversion, `std::hash`, or
`std::uniform_int_distribution` are used. Dataset paths in `corpus.json` are
relative to the repository root. Entries are sorted by their deterministic
dataset IDs and the manifest schema is version 1.

XZ Utils' [`create_compress_files.c`](https://github.com/tukaani-project/xz/blob/master/tests/create_compress_files.c)
is the reference for small, purpose-built test fixtures and reusable byte,
text, and random-data writers. Shinshu follows that approach with explicit
cross-platform rules, manifest checksums, and non-overwrite behavior.

## Commands

```sh
shinshu data generate --all
shinshu data generate --profile pseudorandom --size 65536
shinshu data validate
shinshu data list
shinshu data summary
```

Generation is rooted at the current working directory. Run the command from
the repository root. `--all` creates the 32 primary cases and 9 edge cases.
Single-profile generation accepts sizes from zero through 256 MiB. It adds or
reuses one record without removing prior entries.

Generated files are immutable from the generator's perspective. If the path
already exists, its SHA-256 must equal the generated bytes' SHA-256 or the
command refuses to continue. New files are staged beside their final path and
published without replacing an existing destination. Existing manifests are
parsed and their listed files are checked before an update.

## Validation gates

`shinshu data validate` reports each gate and writes
`data/manifests/validation_report.json`:

- **G01** — each listed file exists and can be read.
- **G02** — actual file length equals `size_bytes`.
- **G03** — SHA-256 equals the manifest checksum.
- **G04** — regenerating from profile, version, seed, and parameters produces
  the exact same bytes.
- **G05** — IDs and paths are unique; paths are safe repository-relative paths.
- **G06** — JSON structure, required fields, and schema version are valid.
- **G07** — listed files still match their deterministic source bytes.
- **G08** — all required profile/size IDs and edge cases are present.

Each gate reports `PASS`, `FAIL`, or `SKIP` with an explanation. A malformed
manifest makes dependent file checks `SKIP`, while schema validity fails.
Any failure or skip makes the overall validation command return nonzero.

The SHA-256 implementation is in the C++ project and checked against standard
empty-input and `abc` test vectors. A checksum detects changes relative to the
manifest; it does not authenticate a manifest changed together with its data.
